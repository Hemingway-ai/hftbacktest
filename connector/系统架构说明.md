# Connector 模块架构说明

> 参考根目录 `系统架构分析.md`，本文件聚焦 `connector/` 子项目。

## 1. 模块定位

`connector` 是实时交易连接层，核心职责：

1. 连接交易所（Binance Futures / Binance Spot / Bybit）的行情与账户通道。
2. 接收 bot 通过 IPC 发来的下单/撤单请求并执行。
3. 将订单状态、仓位、行情统一转换成 `LiveEvent` 再回推给 bot。
4. 维护多流行情融合、订单状态一致性与重连容错。

## 3. 整体架构

### 3.1 分层结构

1. `进程与IPC编排层`：`main.rs`
- 接收 bot 请求（下单/撤单/注册标的）
- 启动交易所连接器
- 将连接器上报事件统一发布到 bot

2. `连接器抽象层`：`connector.rs`
- 统一 trait：`ConnectorBuilder`、`Connector`、`GetOrders`
- 统一消息类型：`PublishEvent`

3. `交易所适配层`：`binancefutures/`、`binancespot/`、`bybit/`
- `mod.rs`：连接器实现与任务组织
- `*_stream.rs`：WS消息处理
- `rest.rs`：HTTP API 调用
- `ordermanager.rs`：订单状态一致性管理
- `msg/*`：协议结构定义与反序列化

4. `基础能力层`：`utils.rs`
- 签名、时间戳、退避重试、解析助手、复合键结构

### 3.2 运行数据流

1. 启动：`main.rs` 读取配置并构建指定连接器。
2. 连接：连接器在后台启动 market/user/private/trade 等流。
3. 请求：bot 发 `LiveRequest` 到 connector（IPC）。
4. 执行：connector 调 REST 或 trade WS 发单/撤单。
5. 回报：交易所回报经 `ordermanager` 合并后发 `PublishEvent::LiveEvent`。
6. 发布：`run_publish_task` 将 `LiveEvent` 广播给 bot，同时维护深度融合快照。
7. 新 bot 注册标的：先回放该标的当前订单/仓位/深度快照，再进入实时流。

## 4. 关键设计点

1. `订单状态一致性`
- Binance/Spot 的 REST 与 WS 是双通道异步回报。
- `ordermanager` 通过 `removed_by_ws/removed_by_rest` 等标记避免重复删除和幽灵单。

2. `行情融合`
- `main.rs` 的 `handle_ev` 使用 `FusedHashMapMarketDepth` 融合多档位/多频率深度流。
- 保证多个 bot 注册同一标的时可获得一致快照和连续更新。

3. `连接健壮性`
- 所有连接任务使用 `Retry + ExponentialBackoff` 自动重连。
- 各流都有 ping/pong 或心跳检测，并在连接中断时上报 `LiveError`。

4. `多交易所统一接口`
- 对 bot 只暴露 `LiveRequest/LiveEvent` 协议，不暴露交易所差异。
- 交易所差异收敛在 `msg` + `rest` + `ordermanager` 内部。

## 6. 与系统其它模块关系

`connector` 是“实盘执行网关”，上游对接 bot（IPC），下游对接交易所 REST/WS。  
与 `collector` 不同，`connector` 不落盘原始数据，重点在低延迟事件传递、订单状态一致性和连接可恢复性。
