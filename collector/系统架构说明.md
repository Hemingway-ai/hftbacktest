# Collector 模块架构说明

> 参考根目录 `系统架构分析.md`，本文件聚焦 `collector/` 子项目本身。

## 1. 模块定位

`collector` 是行情采集进程，职责是：

1. 连接交易所公共 WebSocket 行情流。
2. 在发现深度增量丢包时补拉 REST 深度快照。
3. 将原始 JSON 行情按 `symbol + 日期` 轮转写入 `.gz` 文件。

该模块保持“采集即落盘”的设计，不在进程内做策略逻辑和指标计算。

## 2. 目录树（含文件说明）

    ├── error.rs                        # 采集侧统一错误类型(解析/格式/连接中断)
    ├── file.rs                         # 按symbol管理文件句柄；按天轮转并写入gzip
    ├── throttler.rs                    # 简单滑窗限流器（用于快照补拉频率控制）
    ├── binance/
    │   ├── mod.rs                      # Binance现货消息处理、深度连续性检查、补快照触发
    │   └── http.rs                     # Binance现货REST/WS连接、订阅拼接、重连与ping处理
    ├── binancefuturesum/
    │   ├── mod.rs                      # Binance U本位永续处理逻辑（基于pu/u链路校验）
    │   └── http.rs                     # Binance U本位永续REST/WS连接与重连
    ├── binancefuturescm/
    │   ├── mod.rs                      # Binance 币本位永续处理逻辑（基于pu/u链路校验）
    │   └── http.rs                     # Binance 币本位永续REST/WS连接与重连
    ├── bybit/
    │   ├── mod.rs                      # Bybit主题消息路由；订阅应答失败检测

        └── http.rs                     # Hyperliquid WS订阅、JSON ping/pong、重连退避

## 3. 整体架构

### 3.1 分层结构

1. `入口与调度层`：`main.rs`
- 解析参数：`path exchange symbols...`
- 根据 `exchange` 选择采集模块并启动异步任务
- 统一接收 `(recv_time, symbol, raw_data)` 后写盘

2. `交易所适配层`：`*/mod.rs + */http.rs`
- `http.rs`：底层连接、订阅请求、心跳与重连
- `mod.rs`：消息语义处理、symbol 提取、链路完整性校验

3. `存储与基础能力层`：`file.rs / throttler.rs / error.rs`
- `file.rs`：按天轮转压缩文件，统一写入格式
- `throttler.rs`：滑动窗口限流，控制快照补拉频率
- `error.rs`：解析/格式/连接类错误归一

### 3.2 运行数据流

1. 启动：`main.rs` 解析参数并创建 `writer_tx/writer_rx` 通道。
2. 采集：对应交易所 `run_collection` 建立 WS 连接并持续收包。
3. 处理：`mod.rs::handle` 解析消息，提取 symbol。
4. 补偿：若深度序列不连续，异步调用 `fetch_depth_snapshot` 并受 `Throttler` 限制。
5. 落盘：`file::Writer` 以 `symbol` 为键写入 `path/<symbol>_YYYYMMDD.gz`。
6. 退出：收到 `Ctrl+C` 后主循环停止，文件在 `Drop` 中 flush/finish。

## 4. 关键设计点

1. `增量深度补偿`
- Binance 系列在 `mod.rs` 中维护 `prev_u_map`。
- Spot 使用 `U/u` 连续性；Futures 使用 `pu/u` 连续性。
- 发现断档即补拉 REST depth snapshot，避免仅依赖增量流导致订单簿漂移。

2. `统一原始数据归档`
- 所有交易所最终都写入“时间戳 + 原始 JSON”。
- 不做结构化转换，保证后处理可重放、可回溯。

3. `连接健壮性`
- 各交易所在 `http.rs` 内实现独立心跳策略：
  - Binance：WS ping/pong + 超时检查。
  - Bybit：定时发送 JSON ping。
  - Hyperliquid：JSON ping/pong 语义处理。
- 出错后按错误次数递增 sleep 做重连退避。

4. `并发模型`
- 连接任务与写盘任务通过无界通道解耦。
- 快照补拉使用 `tokio::spawn` 异步执行，避免阻塞行情主接收环。

## 5. 逐文件详细说明

| 文件 | 说明 |
|---|---|
| `Cargo.toml` | `collector` 包元数据与依赖定义（`tokio`、`tokio-tungstenite`、`reqwest`、`clap`、`flate2` 等）。 |
| `src/main.rs` | 程序入口；解析 CLI 参数；按交易所构建订阅模板；启动采集任务；消费通道并调用 `Writer` 落盘。 |
| `src/error.rs` | 定义 `ConnectorError`：`SerdeError`、`FormatError`、`ConnectionAbort`，供各交易所模块统一使用。 |
| `src/file.rs` | `RotatingFile` 负责按日期切换 gzip 文件；`Writer` 负责按 symbol 复用句柄并写入标准行格式。 |
| `src/throttler.rs` | 基于最近 60 秒执行时间戳的限流器，防止快照补拉触发过于频繁。 |
| `src/binance/mod.rs` | Binance Spot 业务处理：解析 `stream.data`，检查 `depthUpdate` 连续性，异常时触发快照补拉。 |
| `src/binance/http.rs` | Binance Spot REST/WS 接口：拉取交易对、深度快照、WS连接、pong响应、断线重连。 |
| `src/binancefuturesum/mod.rs` | Binance U本位永续业务处理：基于 `pu/u` 校验深度链路并触发补快照。 |
| `src/binancefuturesum/http.rs` | Binance U本位永续 REST/WS 实现，含订阅拼接与重连控制。 |
| `src/binancefuturescm/mod.rs` | Binance 币本位永续业务处理：逻辑与 U本位一致，面向 CM 数据源。 |
| `src/binancefuturescm/http.rs` | Binance 币本位永续 REST/WS 实现，连接 `dapi/dstream` 端点。 |
| `src/bybit/mod.rs` | Bybit 数据处理：从 `topic` 末段提取 symbol；校验订阅 `success` 回包。 |
| `src/bybit/http.rs` | Bybit WS订阅发送、定时 ping、pong 回应与重连逻辑。 |
| `src/hyperliquid/mod.rs` | Hyperliquid 数据处理：按 `channel` 识别消息类型并提取 `coin` 作为 symbol。 |
| `src/hyperliquid/http.rs` | Hyperliquid WS订阅构造、JSON ping、过滤 pong、重连退避。 |

## 6. 与上层系统的关系

在整体项目中，`collector` 负责“数据入口”。其产物是原始行情归档文件，后续可由 Python 工具链或回测模块转换、校验、回放。  
因此该模块重点是：连接稳定性、消息完整性、落盘可靠性，而不是策略计算性能。
